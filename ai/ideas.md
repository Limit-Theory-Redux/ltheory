# Project Analysis & Ideas

Analysis of the current state of Limit Theory Redux (branch `feat/multithreaded_rendering`,
2026-07) with prioritized improvement ideas and a design proposal for the upcoming
**navigation** feature. Grounded in the skills under `ai/skills/` and the roadmap in
`ai/multithreaded_rendering.md`.

---

## 1. Project state snapshot

**Architecture** (see `ai/skills/project-overview`): Rust engine `phx` (~32k LOC cdylib)
driven by a Lua game layer over zero-overhead LuaJIT FFI. Bindings are generated by the
`luajit-ffi-gen` proc-macro. Gameplay follows a Lua-side ECS (`script/Core/ECS/` +
`script/Modules/`), with a `script/Legacy/` layer still present in parallel.

**Where things stand:**

- **This branch does not compile** — `cargo check -p phx` fails with 26 errors, all in
  the committed batch-layer work under `engine/lib/phx/src/render/thread/`
  (`render_batch.rs` references a dead earlier design: `WorkerPoolHandle`,
  `RenderBatchApi`, `RENDER_BATCH`; `renderer.rs:422` reads a nonexistent
  `RenderStats.batches_processed`). Diagnosis and a phased fix plan already exist in
  `ai/multithreaded_rendering.md` (§2, §3).
- **The multithreaded renderer is dormant**: complete command executor
  (`render_thread.rs`, ~1.9k lines, ~80 command variants), but nothing at runtime
  submits commands, `--render-thread` exits on startup due to an inverted return in
  `Engine::start_renderer`, and GPU resource creation is unbridged.
- **Render is 40% of the crate** (12.9k LOC) and carries the oldest debt: per-glyph
  font textures (`render/font.rs`), 32-bit-only mesh indices (`render/mesh.rs:397`),
  no mesh merging in `lod_mesh.rs`, a 1k-line `bsp.rs` with unfinished split heuristics.
- **Robustness**: ~73 `.unwrap()` and ~99 `panic!`-family call sites inside a cdylib
  called from LuaJIT — a Rust panic unwinding across the `extern "C"` boundary is UB,
  so each is a potential hard crash. 164 `unsafe` blocks, many tagged `// TODO: remove`.
- **CI is thin**: `.github/workflows/ci.yaml` fast-gates only `cargo +nightly fmt
  --check`; no clippy, no `cargo check`/test job. A non-compiling branch like this one
  is only caught inside the slow per-platform `build.sh` builds.
- **Testing**: ~40 test markers in `phx` vs. 54 in the (much smaller) `luajit-ffi-gen`
  crate. Math/physics/render logic is essentially untested.
- **Dependencies are modern** (winit 0.30, glutin 0.32, rapier3d-f64 0.22, glam 0.29,
  mlua 0.10) but the renderer is legacy OpenGL via `gl_generator`. Two audio crates
  (`kira` + `rodio`) coexist, as do two text stacks (parley/swash and
  freetype + `font.rs`) — both look mid-migration.
- **Game layer**: the modern ECS stack under `script/Modules/` is genuinely good
  (see §3 — most navigation groundwork already exists), but `script/Legacy/`
  duplicates large parts of it (ships, actions, cameras, system map) with no written
  retirement plan.

## 2. Improvement ideas (prioritized)

### 2.1 Now — unblock and protect the build

1. **Restore compilation** on this branch by executing Phase 0/1 of
   `ai/multithreaded_rendering.md`: gut the dead half of `render_batch.rs` (keep
   `RenderBatch`/`BatchStats`/`new`/`add_entity`), fix the `batches_processed` stat,
   invert the `Engine::start_renderer` returns, fix frustum-plane normalization and
   the location `-1` MVP uniform. These are small, fully-specified fixes.
2. **Add a fast CI gate**: one cheap Linux job running `cargo check --workspace`,
   `cargo clippy --workspace -- -D warnings`, and `cargo test -p luajit-ffi-gen`
   before the platform builds. Cost: ~2 min/PR; benefit: broken branches surface in
   minutes, not after three platform builds.
3. **Guard generated bindings drift**: CI step that runs `cargo build -p phx` and
   fails on a dirty `engine/lib/phx/script/ffi_gen|meta/` — enforcing the
   "commit regenerated Lua with the Rust change" rule from `ai/skills/luajit-ffi-bindings`.

### 2.2 Engine robustness (high value for a shipping game)

4. **Panic containment at the FFI boundary.** The generated `extern "C"` wrappers are
   the natural chokepoint: have `luajit-ffi-gen` wrap method bodies in
   `std::panic::catch_unwind`, log via `tracing`, and return a default/abort flag.
   One change in the generator hardens all ~hundreds of entry points at once.
5. **Unwrap/panic reduction campaign** in `phx`, prioritized by blast radius:
   `render/` (GL object creation), `physics/` (raw `*mut RigidBody` handoffs),
   `engine/task_queue/`. Convert to `Result` + `thiserror` (already a dependency);
   `render/mesh.rs:517` even has a "Make `Error` an enum" TODO.
6. **Render-thread error surfacing**: the render thread logs GL errors the main thread
   never sees. Add an error counter to `SharedRenderStats` (or a drained error
   channel) so Lua/HUD can observe failures. (Also listed in
   `ai/multithreaded_rendering.md` §4.)

### 2.3 Performance & quality debt

7. **Font atlas** (`render/font.rs` TODO): texture-per-glyph means a bind per glyph —
   the single most classic 2D perf bug. Alternatively, accelerate the apparently
   started parley/swash migration and delete `font.rs`.
8. **Mesh batching + 16-bit indices** (`render/mesh.rs:397`, `lod_mesh.rs:4` TODOs):
   merge LOD meshes into shared VBO/IBO to kill rebinds; most game meshes fit u16.
9. **Decompose the giant files**: `render_thread.rs` (1.9k), `ui/hmgui/mod.rs` (1.3k),
   `bsp.rs` (1.1k). Straightforward module splits pay off in every future diff.
10. **Evaluate dropping `scalar-math` on glam** where determinism doesn't demand it —
    free SIMD for the math-heavy culling/batching path being built on this branch.

### 2.4 Strategic

11. **Finish the multithreaded renderer via Rust-side interception** (Option B in
    `ai/multithreaded_rendering.md` §5.1): keep the Lua `Draw`/`RenderState`/`Tex2D`
    API and submit commands when `Engine.renderer` is active. Every existing script
    and test then works in both modes; migration is incremental. The alternative
    (porting all Lua draw code to the `Renderer` FFI) is a much larger surface with
    per-entity FFI overhead.
12. **OpenGL → wgpu as the long-term direction.** The command-buffer renderer being
    built is, conveniently, exactly the abstraction layer a wgpu backend would slot
    behind: once all rendering flows through `RenderCommand`, the GL executor in
    `render_thread.rs` becomes swappable. Worth stating as an explicit goal so new
    code doesn't leak GL specifics above the command layer.
13. **Consolidate audio** on one crate (`kira` is the natural keeper for game audio —
    mixing/tweening; `rodio` overlaps) — one less native stack to maintain.
14. **Test the pure logic**: `math/` (472-line `intersect.rs`, octree, the new
    `camera_render_data.rs` frustum code — which had a real normalization bug),
    plus golden tests for the FFI generator's Lua output. Frustum culling and plane
    math are exactly the kind of code unit tests catch cheaply.

### 2.5 Game layer

15. **Write the `script/Legacy/` retirement plan**: inventory what the modern ECS
    stack still lacks (docking, NPC job "Think" AI, economy actions), port or park
    each, and stop new code from referencing Legacy. The navigation feature below
    deliberately ports the last big Legacy behaviors (MoveTo/DockAt) into ECS systems.
16. **Docking** is a hole users will hit immediately: `Dock`/`Undock` are bound in
    `ShipActions.lua` but nothing consumes them. Covered as Phase 2 of navigation.
17. **Persistence groundwork**: no save/load for universe seed + player state.
    Navigation (routes, discovered systems) will want it; a minimal
    seed + player-state snapshot is a good first slice.

## 3. Navigation feature proposal

### 3.1 What already exists (build on it, don't replace it)

The modern ECS stack (wired in `script/States/App/Tests/SolarSystemPlayable.lua`)
already contains most of a navigation system:

| Building block | Where |
|---|---|
| Autopilot: `engageEntity`/`engagePosition`, intercept lead prediction, decel curve, auto travel-drive, HUD telemetry | `script/Modules/Constructs/Systems/AutoPilotSystem.lua` + `AutoPilotComponent` |
| Travel drive (charge/cruise/decel, zone speed caps) | `Constructs/Systems/TravelDriveSystem.lua` + `Physics/Systems/GravityWellSystem.lua` |
| Flight model (thrust/torque → `rb:applyForce/applyTorque`) | `Constructs/Systems/ShipFlightSystem.lua` |
| Player orchestration, camera modes, input blocking while map open | `Constructs/Systems/PlayerController.lua` |
| 2D + 3D system maps with click-to-select → autopilot engage already wired | `CelestialObjects/Systems/SystemMap.lua`, `SystemMap3D.lua` |
| Universe generation (multi-system), children-tree storage, orbital sim, floating origin | `CelestialObjects/Managers/UniverseManager/`, `OrbitalSystem.lua`, `CoordinateRebaser` |
| Zone/trigger volumes | `Spatial/Entities/ZoneEntity.lua`, `TriggerEntity.lua` |
| Design references (do not resurrect, port): `MoveTo`, `DockAt`, `Orbit`, `Patrol`, `Think`, `Action:flyToward` | `script/Legacy/GameObjects/Actions/`, `Legacy/GameObjects/Action.lua` |

**What's actually missing** — and therefore *is* the feature:

- multi-waypoint **routes** (autopilot is strictly single-target),
- **inter-system travel** (universe generates many systems; only one is ever simulated;
  no gates, no way to move between systems),
- a **galaxy map** (only the in-system map exists),
- **docking** (inputs bound, nothing listens),
- **obstacle avoidance** (navigation is straight-line intercept; you can autopilot
  through a planet).

### 3.2 Design principles

- Follow the ECS conventions (`ai/skills/ecs`): dumb components, logic in systems,
  `QuickProfiler` in every system, `EventBus` subscriptions, tuning in
  `script/Config/General/GameConfig.lua` (which already has `shipFlight`,
  `travelDrive`, `autoPilot` sections — add `navigation`).
- **Layer, don't rewrite**: `NavigationSystem` *feeds* `AutoPilotSystem` one leg at a
  time; `AutoPilotSystem` keeps owning steering. Each phase ships something playable.
- Keep it in Lua until profiling says otherwise; the Rust additions in Phase 4 are
  small, targeted FFI exposures.

### 3.3 Phase 1 — Routes & waypoints (pure Lua, ships first)

New in `script/Modules/Constructs/`:

- **`Components/NavigationComponent.lua`** — data only: ordered waypoint list (each:
  `{ pos | entity, arrivalRange, action = "flyBy" | "stop" | "dock" | "jump" }`),
  current leg index, route state (`idle | enroute | paused | arrived`), per-leg ETA
  cache for the HUD.
- **`Systems/NavigationSystem.lua`** — the route stepper: on `Event.PreRender` (like
  other systems), for ships with an active route, check
  `AutoPilotSystem:isActive(ship)`; on leg arrival advance the index and call
  `AutoPilotSystem:engageEntity/engagePosition` for the next leg; fire route events
  (`NavRouteStarted/LegReached/RouteCompleted`) on the `EventBus` for UI/sound.
  Public API: `setRoute(ship, waypoints)`, `appendWaypoint`, `clearRoute`, `pause/resume`.

UI (extend, don't fork, the existing maps):

- `SystemMap.lua` / `SystemMap3D.lua`: **shift-click appends a waypoint** instead of
  replacing the autopilot target; draw the route polyline through remaining waypoints
  (the map already draws the single-target nav line + intercept marker — generalize
  that code); per-leg ETA labels via the existing `UniverseScaleConfig:formatDistance`.
- `PlayerController`/`SolarSystemPlayable`: `AutoPilotToggle` engages the *route* when
  one exists, single target otherwise. Add a `ClearRoute` binding to
  `GeneralActions.lua`.

Playable outcome: plot a multi-stop tour on the map, engage, watch the ship fly it.

### 3.4 Phase 2 — Docking (closes a Legacy gap)

- **`Constructs/Components/DockableComponent.lua`** on `SpaceStationEntity`: docking
  port definitions (local offset, approach vector, radius, capacity, occupancy).
- **`Constructs/Systems/DockingSystem.lua`** — consumes the already-bound
  `Dock`/`Undock` ship actions; state machine per ship:
  `requesting → approach → finalApproach → docked → undocking`. Approach = an
  autopilot `engagePosition` to the port's approach point (parent-relative — the
  autopilot already supports orbiting parents via `parentEntity` + local offset);
  final approach = low-speed `ShipFlightSystem:updateSteeringOnly`-style alignment,
  then kinematic attach (`rb:setKinematic(true)`, parent transform). Port the intent
  of `Legacy/GameObjects/Actions/DockAt.lua`, not its code.
- Use a `TriggerEntity`/`ZoneEntity` volume per port for "in docking range" detection
  rather than distance polling.
- Navigation tie-in: a route waypoint with `action = "dock"` ends the route docked.

### 3.5 Phase 3 — Inter-system travel + galaxy map (the headline)

World model (in `script/Modules/CelestialObjects/`):

- **`Entities/JumpGateEntity.lua`** — a station-like construct with a
  `JumpLinkComponent { targetSystemId, targetGateId }`. `UniverseManager` already
  positions N systems; add a generation pass that builds the **gate graph** (e.g.
  connect k-nearest systems, guarantee connectivity via a spanning tree — standard
  procedural topology) and spawns paired gates in each system.
- **System activation flow**: a `StarSystemManager` (or extension of
  `UniverseManager`) that can *deactivate* the current system (despawn
  meshes/rigidbodies via the existing `SolarSystemVisualizer`, keep the entity tree)
  and *activate* another. The universe already survives as a pure entity hierarchy;
  only the visual/physics materialization swaps. Ship transit = short warp cutscene /
  loading screen (`LoadingScreen` page exists in the UI Router) while the swap runs.
- **Route planning across systems**: Dijkstra/A* over the gate graph in plain Lua —
  at procedural-universe scale (hundreds of nodes) this is microseconds; no Rust
  needed. `NavigationSystem` expands an inter-system route into legs:
  `fly-to-gate → action="jump" → (system swap) → next leg`.

UI:

- **Galaxy map** as a proper UI Router page (`ai/skills/hmgui`):
  `script/UI/HmGui/Pages/GalaxyMap.lua` + views, or — more consistent with the
  existing maps — a `GalaxyMapSystem` alongside `SystemMap.lua` reusing its
  pan/zoom/selection code with star systems as nodes and gate links as edges.
  Click a system → plot route (highlight path) → engage. `CycleMapMode` gains a
  third state: system 2D → system 3D → galaxy.

### 3.6 Phase 4 — Avoidance & polish (small Rust additions)

- **Expose shapecasts to Lua**: `Physics::shape_cast`/`shape_overlap` exist but are
  private (`engine/lib/phx/src/physics/physics.rs:435,461`). Add a
  sphere-cast-with-TOI method to the `#[luajit_ffi_gen::luajit_ffi] impl Physics`
  block (regeneration workflow per `ai/skills/luajit-ffi-bindings`). Autopilot then
  probes its velocity vector each half-second and, on predicted impact, steers via a
  lateral offset waypoint. Planets/stars are few and huge — analytic sphere avoidance
  (deflect around bounding sphere + margin) beats any navmesh here; don't build A*
  in-system.
- **Route smoothing (optional, cosmetic)**: no 3-D curve type exists in `math/` (only
  scalar `bezier3/4` easing in `math/math.rs`). A small `CatmullRom`/`Bezier3D`
  utility — Lua-side first — lets ships bank through waypoints instead of
  stop-and-turn, and lets the map draw smooth route curves.
- **Workers if needed**: if galaxy routing ever grows (per-NPC traffic simulation),
  move planning to a `TaskQueue` Lua worker (`ai/skills/lua-workers`
  send-task/poll-result pattern) — the API boundary (`setRoute` takes a plain
  waypoint list) is already worker-friendly. Not needed for the player-facing feature.

### 3.7 Testing the feature

- Test app per convention: `script/States/App/Tests/NavigationTest.lua` (copy
  `SolarSystemPlayable` setup) — spawn ship + 3 waypoints + a station + two linked
  systems; drive with `cargo run -- NavigationTest`.
- Pure-logic unit surface: gate-graph generation + route planner are deterministic
  functions of a seed — assert connectivity and path optimality in Lua (or extract
  to a testable module).
- Phase 4's Rust shapecast gets Rust unit tests next to `physics.rs`.

## 4. Suggested order of attack

1. Fix the branch build + the five correctness bugs (§2.1 items 1) — everything else
   on this branch is blocked behind `cargo check` passing.
2. Add the fast CI gate + bindings-drift check (§2.1 items 2–3) so this can't recur.
3. Start **Navigation Phase 1** — it's pure Lua, entirely independent of the renderer
   work, and delivers visible gameplay value immediately; renderer phases 2–3 of
   `ai/multithreaded_rendering.md` can proceed in parallel.
4. Navigation Phases 2 → 3 (docking, then inter-system + galaxy map), interleaved
   with robustness items 4–6 on the engine side.
5. Phase 4 polish (shapecast FFI, avoidance, smoothing) once real routes expose the
   need; strategic items (§2.4) as capacity allows.
